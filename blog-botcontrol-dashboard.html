Ein Dashboard statt SSH für Discord-Bots

BotControl-Dashboard verwaltet Discord-Bots über eine dunkle Web-Oberfläche: Status, Konfiguration, Live-Logs und Statistiken, ohne dass man sich für jede Kleinigkeit per SSH auf den Server verbinden muss. Der Name ist Programm — es ist "Phase 1" einer geplanten Multi-Bot-Plattform, und diese Phase 1 sieht bewusst anders aus, als man erwarten würde.

Klein anfangen heißt: wirklich klein

Die naheliegende Wahl für ein "Verwaltungs-Dashboard" wäre Postgres, Redis für Sessions/Queues und ein Frontend-Build-Schritt mit irgendeinem Framework. Alles drei fehlt hier absichtlich. Das Dashboard läuft auf demselben kleinen VPS wie der Bot, den es verwaltet — jede zusätzliche Abhängigkeit ist ein zusätzlicher Dienst, der überwacht, aktualisiert und im Zweifel um 3 Uhr nachts neu gestartet werden muss.

Statt Postgres kommt node:sqlite zum Einsatz — das eingebaute SQLite-Modul von Node.js. Kein natives Kompilieren, keine zusätzliche Systemabhängigkeit, eine Datei statt eines Datenbank-Prozesses. Für die erwartete Last (ein Admin-Team, nicht tausende gleichzeitige Nutzer) ist das nicht nur ausreichend, sondern die robustere Wahl.

Entscheidung Vanilla JS/HTML/CSS im Frontend, kein Build-Schritt. Ein Edit in der Datei ist ein Edit, das sofort im Browser sichtbar ist — kein Watch-Prozess, der zwischen Server und Dashboard mitlaufen muss.

Zugriff über Discord selbst regeln

Statt eine eigene Nutzerverwaltung mit Passwörtern zu bauen, läuft der Login über Discord-OAuth2. Zugriff bekommt nur, wer auf dem verwalteten Server eine berechtigte Rolle hat (Owner/Administrator/Moderator, über eine Rollen-ID konfigurierbar). Das erspart ein zweites Identitätssystem — die Rolle, die im Discord-Server sowieso schon über Rechte entscheidet, entscheidet auch hier.

Kontrolle ohne Shell-Zugriff

Start, Stopp und Neustart eines Bots laufen über systemd im Hintergrund — ein Klick im Dashboard statt eines SSH-Befehls. Konfiguration (Kanal-/Rollen-IDs, Feature-Toggles) lässt sich direkt im Browser bearbeiten und landet in der .env-Datei des Bots. Eine bewusste Grenze dabei: Tokens, API-Keys und Passwörter bleiben in der Oberfläche grundsätzlich unsichtbar und nicht editierbar. Bequemlichkeit hört an der Stelle auf, wo sie zum Sicherheitsrisiko würde.

Live-Logs sind ein journalctl-Ausschnitt mit Auto-Refresh, Statistiken zeigen Command-Nutzung pro Tag/Befehl als Chart (Chart.js über CDN, auch hier kein Build-Schritt nötig) sowie einen Fehlerzähler. Sessions laufen über JWT in einem httpOnly-Cookie — nicht im Local Storage, wo ein XSS-Bug den Token direkt auslesbar machen würde.

Was "Phase 1" wirklich bedeutet

Jede der schlanken Entscheidungen hier ist reversibel: Wenn aus einem VPS mit einem Bot irgendwann eine echte Multi-Bot-Plattform mit mehreren Kunden wird, lässt sich node:sqlite gegen Postgres tauschen, ohne die Architektur der Routen anzufassen. Bis dahin ist jede Abhängigkeit, die nicht gebraucht wird, eine Abhängigkeit weniger, die etwas kaputt machen kann.
